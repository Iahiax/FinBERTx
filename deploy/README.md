# نشر FinBERTx على VPS Linux

ابدأ محليًا في Paper، ثم اختبر نسخة احتياطية من قاعدة SQLite وإعدادات التشغيل قبل النشر. لم تُختبر جلسات Capital.com أو WebSocket أو إرسال أوامر Demo/Live في هذه المراجعة.

```bash
sudo useradd --system --home /opt/finbertx --shell /usr/sbin/nologin finbertx
sudo install -d -o finbertx -g finbertx /opt/finbertx
# انسخ ملفات المشروع المراجعة إلى /opt/finbertx ثم ثبّت متطلباته في بيئة افتراضية.
sudo install -o finbertx -g finbertx -m 600 /dev/null /opt/finbertx/.env
sudo systemctl enable --now finbertx
sudo journalctl -u finbertx -f
```

راجع `deploy/finbertx.service` وتأكد من مسارات البيئة قبل تفعيل الخدمة. لا تضع بيانات اعتماد في GitHub أو `.env.example`؛ ضع القيم الجديدة فقط في `.env` ذي الصلاحية `600`.

## تدرج التشغيل

1. ابدأ بـPaper، ثم استخدم بيانات Demo للقراءة فقط لفترة طويلة لمراجعة التغطية والسجلات. القيم الابتدائية المحددة في `.env.example` هي مركز واحد وأمر وسيط واحد يوميًا.
2. إذا قررت اختبار إرسال أوامر Demo، يستخدم البرنامج مجموعة اعتماد Capital.com نفسها (`CAPITAL_API_KEY`, `CAPITAL_IDENTIFIER`, `CAPITAL_PASSWORD`) ويختار مضيف Demo بحسب الوضع. فعّل الإرسال عمدًا عبر `ENABLE_DEMO_ORDERS=true`، ثم اختر `/mode demo` من محادثة Telegram خاصة مسموح بها. استخدم أداة واحدة وحدودًا صغيرة، وراجع كل نتيجة يدويًا.
3. لا تنتقل إلى Live إلا بعد مراجعة مستقلة ومرحلة Demo مطولة. يستخدم Live مجموعة الاعتماد نفسها لكن مع مضيف Live؛ يظل Live معطلًا افتراضيًا ويتطلب بواباته وقائمة Telegram خاصة وتأكيدًا ثانيًا مؤقتًا. لا يبقى الوضع الحي مسلحًا بعد إعادة التشغيل.

الرافعة الورقية 100:1 سقف أقصى وليست هدفًا. حد التعرض لكل أداة يقيّد حجم أوامر Paper والوسيط، وحد خسارة اليوم مطبق على دفتر Paper فقط؛ لا تعتمد عليه لحساب الوسيط أو على خسائر المراكز الخارجية/العائمة. تحقق من الرصيد والمراكز لدى الوسيط بنفسك قبل أي إجراء، خصوصًا إذا ظهرت نتيجة إرسال ملتبسة.

`/backtest <EPIC>` يرسل تقريرًا نصيًا سعريًا متعدد الأطر. لا يرسل البوت ملفات CSV؛ مدخل CSV المحلي، إن استُخدم، يبقى لمسار CLI فقط. هذا الاختبار ليس اختبار FinBERT تاريخيًا.
